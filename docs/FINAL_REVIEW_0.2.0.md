# JJ Music 0.2.0 终版审阅记录

审阅范围：主进程与 IPC、SSRF 与域名守卫、媒体访问与本地文件读取、曲库与设置持久化、歌词写入、在线下载与封面抓取、公开歌单导入、音源宿主与脚本隔离、桌面歌词浮窗、构建与 Windows 分发配置（Electron 运行时、electronFuses、成品调试面）。本轮是一次**安全审查**，不是功能审查 —— 功能面在 0.1.7 那轮已经审过。

审查对象是 `origin/main`（`c5edf00`）到 `808a5e1` 的 31 个提交，共 15 条发现，按级别归为：高 2、中 5、低 8。其中 **F1（艺术家头像不钉来源域名）与 F15（头像记录表无上限）是这 31 个提交引入的**，其余 13 条在 `origin/main` 里已经存在（逐条用 `git show origin/main:<path>` 与 `git diff --name-status` 核过）。

> **方法上的诚实边界**：本次是**手工通读 + 针对性复现**，**没有任何自动化安全扫描器覆盖过这批提交**。所有结论要么有可复现的命令，要么在报告里点名了它只是推理。

## 本轮修复

1. **艺术家头像与歌单封面的抓取按平台钉住来源域名**（F1，高，本次引入）。两处从平台 JSON 里读回来的图片地址直接开抓，没有 `allowedHosts`。现在统一走 `cover-fetch.ts` 导出的 `COVER_HOSTS`：拿不到这个平台的域名表就当作「该平台没有头像」直接不抓，与封面那一半同口径。这是本次唯一一条能实际外泄数据的洞 —— 可以在编译产物上用真实 HTTP 服务器复现出把内网响应体读回来。同一形状的第二个洞在 `playlist-import.ts` 的歌单封面，一起修了。

2. **URL 守卫剥离主机名的尾点**（F2，高，预存在但本次变可达）。`new URL('http://localhost.:1887/x').hostname` 返回的是 `'localhost.'`，黑名单里的 `localhost`/`.local`/`.internal` 一个都不匹配，`isIP` 也判否 ⇒ 放行。实测 `http://localhost.:1887/x` 与 `http://metadata.google.internal./x` 都能通过守卫并拿到响应体。新增 `normalizedHost()` 同时用在黑名单与允许表两侧，尾点在两者里都不再是绕过手段。允许表侧另有边界：`isHostAllowed('migu.cn.', ['migu.cn'])` 为真，`'evil-migu.cn.'` 为假。

3. **成品 exe 的调试端口补上 `isDev` 门**（F3，中）。`JJ_DEBUG_PORT` 一个继承来的环境变量就能在打包后的应用上开出 CDP —— 实测启动 `release/win-unpacked/JJ Music.exe` 并带该变量，`GET /json/version` 返回 200。CDP 落在主进程上意味着以应用的完整 Node 权限远程执行代码。现在只有开发构建会读它，打包探针要走这条路必须显式设 `JJ_ALLOW_DEBUG_PORT=1`。

4. **成品 exe 不再接受命令行传来的 `--remote-debugging-port`**（F4，中）。这条比上一条麻烦：Chromium 在自己解析命令行时就把开关收下了，早于应用的任何一行代码，所以「不 append」没有用，必须用 `app.commandLine.removeSwitch()` 收回，且必须在 `app.ready` 之前。无条件删除会连开发期的调试方式一起废掉，所以它是「应用决定要用的那个端口」的 `else` 分支。

5. **补上 `electronFuses` 配置**（F5，中）。此前仓里一处都没有，成品跑的是 Electron 的默认值：`RunAsNode` 开、`EnableNodeOptionsEnvironmentVariable` 开、`EnableNodeCliInspectArguments` 开、asar 完整性校验关、`OnlyLoadAppFromAsar` 关 —— 实测 `JJ Music.exe --inspect=9444` 能拿到活着的 Node inspector。现在后四项全部收紧，`runAsNode` **刻意保留开启**：音源宿主靠 `fork()` 启动并自己设 `ELECTRON_RUN_AS_NODE`，关掉它会连带打断主进程的 `process.fork()`。

6. **Electron 38.8.6 升级到 42.11.8**（F6，中）。`npm audit --omit=dev` 报 0 在这里是假的：`electron` 是 devDependency，而 electron-builder 会把装出来的那个二进制原样拷进成品，用户跑的正是它。38.8.6 落在公告受害区间内。升版后 fuses 读回实测：`EnableNodeOptionsEnvironmentVariable`、`EnableNodeCliInspectArguments`、`EnableCookieEncryption` 全为禁用，`EnableEmbeddedAsarIntegrityValidation` 与 `OnlyLoadAppFromAsar` 为启用。

7. **损坏的配置文件改成留档，而不是静默清空后覆盖**（F2 之外的独立发现）。原来的读取路径无法区分「文件不存在」和「文件被截断」，两者都返回空状态，于是下一次写入就把用户真实的歌单和曲库索引覆盖掉了。新增 `readJsonFile()`：ENOENT 返回 `undefined`，解析失败则把原文件改名为 `<名字>.corrupt-<时间戳>` 并记一条错误。设置、歌单、曲库索引三处都接上了，配两条回归测试断言「旧文件被原样留档」与「默认值确实生效而不是把损坏数据当成空数据」。

8. **曲库封面改为原子写**。`writeCover()` 原来直接 `writeFile`，而文件名的内容寻址摘要就是名字本身 —— 半张 JPEG 一旦落盘，就会因为 `existsSync` 为真而被永远当作合格封面提供出去，而且任何正确的字节都不再可能哈希到同一个名字。

9. **拖入 `.lrc` 的读取改走媒体白名单**。这是全仓唯一一个跳过了 `allowedMediaPath` 的歌词读取通道：路径来自渲染层，随后文本会被写进曲库目录、再由白名单内的接口交回。要求路径属于「渲染层已被允许读取」的那一类就关上了这个洞，而真实拖入仍然通过。

10. **歌词写入加 1 MiB 上限**。三条渲染层可触发的歌词写入通道都没有大小限制，而下游的标签写入器对 `unsynchronisedLyrics` 不做任何检查。超过上限的歌词在导出前被摘掉并附一条说明，而不是让一个畸形文件把写标签整条路带崩。

11. **桌面歌词浮窗补齐 `setWindowOpenHandler` 与 `will-navigate`**（F14，低）。主窗口一直有这两道，浮窗一直都没有，是不该存在的不对称。今天它不可达（浮窗的 CSP 只允许 `connect-src 'self'`，远端写入只走 `textContent`），补上是为了让它以后也不会可达。

12. **头像记录表加上条数上限**（F15，低，本次引入）。这张表每次写入都整份重写，却没有上限；对照同类实现 `pending-assets.ts` 用的常量是 500。现在按最旧写入淘汰，上限 4000。

13. **下载嵌入封面按平台钉住域名**（F13，低）。下载管理器自己知道 `track.source`，所以由它决定钉什么、注入的 `fetch` 只负责转交：封面来自每个平台一小撮已知图床，而音频地址合法地活在音源挑的中继上 —— 两种保证不能焊进同一个函数。新增 `guardedFetch()` 把 `allowedHosts` 从浏览器 `init` 里取出来再转交。实测的坑值得记下来：多出来的键如果留在 `init` 里，`fetch` 会一声不响地丢掉，请求就真的不钉域名，而且不会有任何报错。

14. **`SHA256SUMS` 的版本过滤改成 `-<版本>-`**（F9，低）。原来用子串匹配，实测 `'JJ-Music-0.1.10-Setup-x64.exe'.includes('0.1.1') === true` —— 写 0.1.1 的校验和时会把 0.1.10 的残留一起算进去，而 `release/` 从来不被清理。

15. **CI 的 actions 从 tag 钉改为 SHA 钉，并关掉凭据持久化**（F10，低）。缓解事实照实记：该工作流本来就只有 `permissions: contents: read`，且全文没有引用任何 `secrets.*`。

16. **顺带修掉两处「已记账、一直没修」的接口谎话**。这两条与安全审查无关，是在同一轮里一并处理的：一是 kw / kg 搜索行的 `size` 传的是字面量 `1`，导致下载子菜单把每首歌都显示成「0.00 MB」—— 现在用 `true` 表示「这一档确实存在、尺寸未知」，并顺手把判据从 `!bytes || bytes <= 0` 改成能识别 `NaN` 的写法；二是播放页那行显示的是**请求的**档位（默认 `flac24bit`）而不是**实际拿到的**档位 —— 现在在解析结果落回播放状态之后读它，UI 显示实际值、回退时才显示请求值。

## 性能与测量

0.2.0 没有引入新的性能优化，这一节是对既有优化在本版构建上的一次复测，口径与上一轮相同：`node tools/benchmark-ui.mjs` 使用 10,000 首合成曲目、每轮 50 次查询、3 轮中位数，并逐条校验优化前后结果一致。本机一次测量：

| 项目 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 50 次搜索中位耗时 | 253.26 ms | 48.95 ms |
| 搜索索引首次建立 | — | 6.15 ms |
| 101 次快速设置更新的 IPC 写入数 | 101 | 2 |

搜索专项约快 5.17 倍。同一份基准在 0.1.7 那轮记录的是 217.40 ms → 45.05 ms（4.83 倍）、索引 2.71 ms —— **两次测量都是真数字，差异来自机器负载而不是代码**，所以两轮都记录在这里而不是取一个当唯一的真值。此为合成数据基准，真实收益随曲库、关键词和机器变化；没有将它等同于整个应用的性能提升。

本轮唯一与「规模」相关的改动是头像记录表加了上限（第 12 条）。它此前会随使用无限增长，而这**不是一个耗时数字**，所以没有放进上表：变化的是上界（无界 → 4000 条，按最旧写入淘汰），不是速度。

## 验证结果

- 类型检查、生产构建通过；离线测试 **27 / 27 套件通过**（0.1.7 时为 26 套，本轮新增了 `url-guard` 与持久化回归的用例）。
- 端到端：**40 项通过，0 失败**；随后恢复干净生产构建并确认测试钩子在成品里**不可达**（`E2E hook reachable in this build: NO (clean build)`）。其中「在线搜索」一项两次尝试都拿到第三方返回的 `HTTP 500`，而这一项**按设计区分**「我们的链路断了」（bridge 抛错）与「上游此刻不正常」（干净的空结果），所以它断言的是「IPC 通道可达」加上「失败以结构化错误浮出、而不是崩溃」—— 两条都通过。同一天另一个人工探针（`clean-profile-sources.mjs`）也在这条链路上失败过两次，且两次的报错文本不同 ⇒ 这是**第三方音源侧的真实抖动，不是本地回归**。
- 人工窗口检查 `node tools/probe/salt-ui-smoke.mjs`：**71 项通过，0 失败**。包括「成品里测试钩子不可访问」「设置通道改不动曲库白名单」、桌面歌词卡片的悬停/锁定/底板一整组、平台验证状态、以及干净退出（未完成任务 0，退出码 0）。
- 成品调试面 `node tools/probe/check-packed-surface.mjs`：**4 个场景全部符合预期**。这个探针的第 4 个场景是控制组 —— 前三个场景量的是「本该没有回答」，而一个根本没启动的构建同样不回答，所以必须有一组 `JJ_DEBUG_PORT` + `JJ_ALLOW_DEBUG_PORT=1` 证明这个测量确实看得见 CDP。三个否定场景（环境变量、argv 的 `--remote-debugging-port`、argv 的 `--inspect`）都静默，控制组正常应答，且四个场景在窗口关闭那一刻进程都仍在运行。
- `npm audit` 报 `found 0 vulnerabilities`。**这个 0 不能单独当作结论**，理由见第 6 条：`electron` 不在它的覆盖范围内。
- 已生成 `SHA256SUMS.txt`（2 个文件），格式为 `sha256sum -c` 可直接校验。
- 测试与探针都使用独立配置副本，没有覆盖用户正在运行的旧版目录。
- 复现：`npm run verify`、`npm run test:e2e`、`node tools/probe/salt-ui-smoke.mjs`、`node tools/probe/check-packed-surface.mjs`（需先有 `release/win-unpacked`）、`node tools/benchmark-ui.mjs`（基准需先运行测试以生成测试模块）。

## 结论与已知边界

本轮审阅与验证没有发现阻塞当前版本发布的问题。这是当前功能范围的终版构建，不代表可以证明软件在所有环境中没有缺陷。

**本次记录但未修的两条**：

- 发布产物未签名，`SHA256SUMS.txt` 与二进制同源（F7）。校验和对「文件损坏」和「第三方镜像换了文件」有效，对「GitHub 账号被攻陷」无效。签名需要证书，不在本轮范围内。
- `relaxCorsForMedia` 对媒体响应定点注入 `Access-Control-Allow-Origin: *`（F12）。它只在原本没有该响应头时注入、且不设 `Allow-Credentials`，作者在代码里写明了为什么用定点注入而不是关掉 `webSecurity`。这是刻意保留的放宽，照实记录。

**作者已经写在代码里的两处残留风险**（不计作本轮发现）：

- URL 守卫校验的是主机名，不是解析结果，因此理论上存在 DNS 重绑定窗口（`url-guard.ts` 自己写明了这一点）。
- 音源脚本以用户权限运行，是纵深防御而不是沙箱（`source-host.ts` 自己写明「This is defence in depth, not a sandbox」）。

**外部依赖与既有限制**：在线音源与公开歌单依赖外部服务，本轮实测中第三方音源连续两次返回 `HTTP 500` —— 这类失败会表现为「在线播放不了」，与本版代码无关。下载目前从头重试，不支持断点续传；嵌入歌词和封面支持 MP3 / FLAC，其他格式显示限制提示。免安装版在完整解压后运行，默认与安装版共用用户配置，不是把所有用户数据写入 ZIP 所在目录。

已验证安装器构建和内部数据、同版本程序实际运行；未在用户当前环境执行安装或卸载流程，以免改变其已安装版本与快捷方式。
