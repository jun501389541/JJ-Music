# OR8：待写入资源容量与持久化保护

日期：2026-10-16。对应 OR-10、RR08、RR16。范围为生成测试资料中的 PendingAssetStore，不操作日常队列或歌曲文件。

## 问题与改动

旧队列 add 会先把结果放进内存，再按最早时间删除条目以满足容量，最后写盘。它把待写入资源当作可回收缓存，违反设计6.4与6.7。另有两条受控回归确认：首次 load 尚未完成时，第二次 load 提前返回，使并发 add 可能覆盖磁盘原队列；写盘失败后，未保存的修改仍留在内存，并可能进入后续成功快照。

保持已有容量数值：500 条、总歌词 2,000,000 字符、单条歌词 200,000 字符。新行为：

- 入队或同键替换后若超额，拒绝本次修改并明确提示先写入或丢弃部分条目；保留原内存和文件，不淘汰旧选择。
- 单条超长也明确报错，避免原先静默跳过却让上层显示已待写入。
- 所有队列/丢弃指纹变更在串行队列中计算副本，原子写盘成功后才发布内存状态；失败不污染下一次操作。
- 首次并发加载等待同一个读取 Promise。无实际变化的操作不重写文件。
- 正常退出、复制资料目录迁移前，先排空待写入队列自身的变更，再由既有全局写入门禁收尾。

主进程 stageFetchedLyric 已有 await add，成功后才设置 pending 并装饰歌词缓存；本轮没有改写该流程。NowPlayingView 的手动选词已有异常提示，播放器的自动歌词读取也已有异常状态。容量拒绝通过既有错误路径反馈，本轮没有声称完成容量已满时的渲染UI实测。自动查词暂存失败时，此次歌词读取可显示失败；音频播放路径不依赖这个队列，没有新增写标签行为。

## 回归证据

src/test/pending-asset-capacity.test.mts 使用 tools/build-test.mjs 打包的生产模块。全部使用临时目录、生成的条目与歌词，无真实脚本或外部端点：

1. 500 条队列拒绝第501条，原文件字节与重启结果不变；容量内同键替换仍成功。
2. 总字符已满时拒绝使其溢出的替换；缩小旧文本后可接受新文本。
3. 已存在501条的历史文件不因下一次 add 被截断。
4. 以非空目录阻挡目标原子重命名，验证失败时旧内存/文件保留，恢复存储后下一次 add 不夹带失败内容。
5. 并发首次 load/add 不覆盖已有条目。
6. 并发竞争最后一个名额，仅一个成功；其余499条及成功者均保留到重启。
7. 单条200001字符明确拒绝，原选择保留。
8. 删除、记录丢弃和清空依次写盘失败，原选择与丢弃决定均保持不变。
9. 生命周期 flush 在两项变更尚未到达全局写盘器时调用，返回后两项都已落盘。

前6项在正常权限的旧实现中全部失败，失败包括预期拒绝未发生、失败修改残留、并发覆盖；修复后9/9通过。单条超限项也另行确认旧行为缺少拒绝后才修复。日志：`.cache/pending-asset-capacity-red-host.log`、`.cache/pending-asset-capacity-green-final.log`。沙箱首轮因Windows原子替换被EPERM阻止，保留于red.log，未把这个环境错误当作功能缺陷证据。

独立代码复核发现新串行队列还需衔接退出/迁移：生产打包模块受控实验中，仅全局flush返回后磁盘只有first，等待全部add后才出现second。已新增store.flush并接入main/index.ts两处门禁，第9项回归先确认缺少接口失败、修复后通过；复核该修补后未再发现阻断问题。它等待已排队变更，不将应用继续接收新请求时的任意未来写入视为已完成。

最终 `npm run verify` 退出0：类型检查、生产构建、86/86离线套件和5/5门禁通过，日志为 `.cache/pending-asset-capacity-verify-final.log`。包含既有asset-export、local-lyric-cache和source-owner-lifecycle回归。`git diff --check` 通过；只读检查本轮jj-pending-cap专用临时目录剩余0。GraphFlow已增量索引。没有提交、推送、安装或发布。

## 保留边界

- 已有损坏/不可读队列文件的读取回退策略未在本轮改造，不能据此宣称任意损坏或读权限故障都已保全。
- 后续[读取保护](OR8-pending-read-recovery.md)已单独补齐首次损坏/读取错误阻止覆盖与同实例重试；不自动修复未知损坏内容。
- 串行顺序覆盖单个应用服务实例；多个实例同时写同一目录、批量标签写入完成后按旧快照移除新选择的情形未在本轮解决。
- 后续[快照保护](OR8-pending-snapshot.md)已单独修复旧任务清理新选择及丢弃指纹竞态，未将多个任务写同一歌曲文件的顺序问题混为已解决。
- 未修改容量参数、手工歌词/封面优先级或已保存歌曲文件。人工听感、日常资料UI验收和真实源更新回退仍未通过本轮验证。
