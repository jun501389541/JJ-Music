# OR8：同文件资源写入串行保护

日期：2026-10-16，对应 OR-10、RR08/RR16。补充旧快照保护未覆盖的同文件写入边界，不操作日常资料。

## 复现与实现

旧exportAssets在existsSync检查与异步写入之间没有排队。两个noClobber任务会同时看到侧车不存在，随后均返回成功，后写覆盖先写。同basename的MP3/FLAC也共享同一个LRC，不能仅按音频文件名互斥。标签读改写则共用固定.jjtmp，两个补丁并发会争用临时文件。

新增PathTaskQueue，一次为全部受影响路径预留位置，等待相交旧任务；相互独立的路径仍可并行。键用绝对规范化路径，Windows忽略大小写。任务失败向原调用者报告，队列尾部消化失败以便后续任务继续，释放时只解除仍属于本任务的尾部；flush等待执行中和未开始的任务。

exportAssets整次检查、标签读改写、备份及侧车发布在同一个队列操作内，目标包括audioPath、同stem LRC、可选stagingPath及所请求的封面路径，避免只保护临时文件重命名却仍读取旧标签。

主进程另设外层同曲提交队列，把资源导出、最新索引读取合并、索引更新及待写入清理串在一起。待写入快照与写入设置在调用时捕获，不能等前面的任务完成后重新获取新选择作为清理权限；进入队列后使用最新曲目索引合并来源记录。两个队列是不同实例，按外层到内层获取。

独立复核指出：下一首歌词准备或匹配资源获取期间，文件队列可能暂空，单等队列不能代表整次操作完成。新增TaskGroup同步登记整批资源写入、全部待写入、匹配应用及已确认歌词导入；歌词导入的文件对话框尚未确认时不登记，避免退出等待用户尚未决定的操作。迁移与退出先等这些生产者及外层提交完成，再等待资源导出、待写入和JSON写入；下载的既有shutdown仍保留。复核该补丁后无新增P1/P2阻断。

## 生产回归证据

新asset-write-concurrency.test.mts打包导入生产exportAssets、PathTaskQueue和TaskGroup，7/7通过：

1. 同音频路径的两次noClobber歌词导出，只有首次成功，侧车保留首次文本。
2. 不同音频格式、同stem共享LRC时，同样只保留首次成功。
3. 两个真实生成FLAC写入分别设置title/artist，均成功且两字段保留；.bak字节等于原文件，未残留.jjtmp。
4. 多目标相交队列保持调用顺序，独立目标可在前任务暂停时先完成。
5. 前任务拒绝后，后任务和flush仍完成。
6. 规范化路径（Windows含大小写）识别为同目标，flush等待正在执行及排队任务。
7. 用闸门暂停下一次写入前的准备阶段，即使文件队列已空，整次操作排空仍等待准备完成和后续写入。

最初三项在旧生产模块中全部失败：两项noClobber都成功两次，FLAC两次写入后title字段丢失；修复后通过。生产者排空接口也先确认缺失后实现。日志：`.cache/asset-write-concurrency-red.log`、`.cache/asset-write-concurrency-green-final.log`。只有生成的测试FLAC与文本被写入，没有运行真实音源或处理用户歌曲。主进程入口和退出/迁移接线由类型构建与独立源码复核验证，不把队列单测当作实际UI并发写入验收。

最终 `npm run verify` 退出0，类型检查、生产构建、89/89离线套件和5/5门禁通过，日志为 `.cache/asset-write-concurrency-verify-final.log`。`git diff --check` 通过，测试专用jj-asset-serial临时目录只读核对剩余0。GraphFlow已增量索引。没有提交、推送、安装或发布。

## 保留边界

- 进程内路径排队不等于跨进程文件锁，不保证与外部编辑器同时写入的安全性，也不解析符号链接/硬链接指向同一物理文件的别名。
- 同曲主进程提交按队列顺序完成，不引入文件版本冲突提示或撤销功能，也不替代用户确认写入。
- 未改动资源优先级、容量、快照CAS和损坏读取保护。人工听感、日常实际资料交互、安装升级及真实源更新回退仍按OR8记录保留。
