# JSON 歌单备份导入恢复设计（2026-10-24）

状态：用户已确认“按此设计直接实施”，采用恢复为新歌单，不覆盖现有内容。

## 行为与取舍

在歌单管理新增“从 JSON 恢复”。使用现有 JJ-Music v1 信息备份格式，支持单歌单或全部备份；原生选择文件后先展示文件名、创建时间、歌单名称及曲目数、总数，再由用户确认导入。

建议首版始终新建歌单而不覆盖：保留备份中的曲目顺序、曲目身份和平台来源，但给每个恢复歌单生成新的 ID，名称加“（恢复）”（若追加会超过4096字符则保留原名，不截断），追加到现有歌单之后。收藏和默认列表也恢复为普通副本，不自动修改当前收藏、默认列表或播放器队列。同名歌单分别恢复，不静默去重。一个备份内重复的歌单 ID 或同歌单重复的曲目身份视为损坏，拒绝且不截断；本地与在线及跨平台相同原始 ID 仍独立。

替代方案是按歌单 ID 覆盖或合并。它会改变现有收藏与顺序，需要额外的冲突预览及覆盖回退，因此本阶段建议不提供。此设计的“恢复”指从信息备份重新创建歌单，不是完整资料目录恢复。

## 数据校验和文件读取

- 仅接收主进程原生选中的单个 .json 文件；渲染进程不提交路径、原始曲目或 JSON 内容。
- 只接受 kind=jj-music-playlists、version=1，合法创建时间和 single/all 范围；单个范围必须恰好1个歌单。空的全部备份提示无需恢复。
- 最大20MiB原文件、1000歌单、50000曲目，读取实际字节同样有界；未知版本、缺字段、损坏数值/标识/类型和超限整体失败。UTF-8 BOM可接受；不能用恢复入口读取任意脚本或扫描音乐目录。
- 显式校验本地/在线 kind 与路径/来源的一致性；重用已有导出白名单保留安全基础资料和已知原生标识，忽略未知字段、providerData、播放URL、图片/歌词和缓存路径。构造新对象，不将任意输入属性并入应用状态。
- 本地绝对路径原样保留，不读取音乐文件、不自动重定位/下载；缺失文件仍是缺失引用，可沿用现有重新定位功能。在线音乐仍需现有音源解析，不恢复资源地址或脚本。
- 不恢复播放器设置、侧栏自定义排序、封面文件、歌词文件或播放历史。

## 主进程预览与持久化

主进程保存已校验的不可变快照，只向界面返回摘要及随机一次性令牌；最多一个待确认快照，令牌有时限。重新选择、取消、退出页面应释放所属令牌，迟到选择结果也仅释放自己。确认后直接使用预览时的快照，即使原文件随后改变也不会偷偷换数据。令牌消费在入队前完成，重复点击不重复导入；持久化失败要求重新预览。

PlaylistStore 新增单次批量事务：在现有 changes 队列内分配新 UUID 和追加 position，一次原子保存全部恢复歌单，失败恢复全部内存状态；与现有重命名、移除、重排互斥排队。成功结果仅返回新建歌单数量、曲目数量及新 ID，不触碰其它资料或当前队列。恢复时应用正退出/本地重新定位维护则拒绝。

界面先显示预览，再明确提示将创建新歌单及本地路径可能失效，确认后保存。持久化成功但界面刷新失败要明确区分“已恢复，列表刷新失败”，避免用户以为没保存而重复恢复。

生产构建离线全套验证，并用独占生成资料的生产 Electron 探针验证原生选择取消、预览无写入、确认后完整新建、系统列表不覆盖、原队列不变、损坏/失败重试、退出释放。只使用生成的JSON/WAV，不读取个人音乐或执行真实音源，真实播放/听感仍单独待验。
