# 当前队列手动切歌交叉渐变设计

日期：2026-10-26。状态：用户已批准本设计，独立 Builder Check 已通过；实施与自动验证完成，人工听感待验。

基础：[自动交叉渐变设计](2026-10-26-crossfade-design.md)、[0.6.0 发布与验收](../../development/2026-10-26-v0.6.0-release.md)。

## 意图与已确认决定

用户选择继续开发手动切歌交叉渐变，并确认：

1. 首版仅覆盖当前队列的上一首、下一首和队列内点选。
2. 新曲仍在解析或缓冲时，旧曲继续播放；新曲可播后再渐变。准备失败留在旧曲。

目标是在上述操作中复用 0.6.0 双通道能力，同时保持取消、完整歌曲身份和现有队列行为可靠。人工听感继续待验。

## 方案比较

| 方案 | 取舍 | 决定 |
| --- | --- | --- |
| 当前队列内手动交接 | 复用当前队列身份和现有双通道，不引入整份队列的提交/回滚 | 用户选择 |
| 同时覆盖换歌单与搜索点歌 | 还需处理新旧队列、历史页和试听模式的提交与回滚 | 不纳入首版 |
| 只在自动下一首已经预载时复用 | 工作更少，但多数手动点选仍不能渐变，行为难以预测 | 不采用 |

## 范围

- 覆盖下一首，以及实际切换到另一曲的上一首；媒体键、托盘和界面入口最终走同一套动作。
- 覆盖当前队列及其筛选结果的曲目点选，按完整条目身份定位，不能把筛选位置当完整队列索引。
- 上一首在没有待切目标、当前进度大于 3 秒时，沿用重播当前曲的规则，不生成双通道交接。
- 切换整张歌单、从搜索/曲库开始新队列、恢复历史队列/会话、自动重试和错误恢复不使用本次手动交接。
- 仅明确的用户手动意图可以启用该路径；不能仅凭 `playTrackAt()` 被调用就判断为手动操作。实现时需核对并标记相关调用边界。
- 不支持交叉渐变能力的引擎、旧曲未实际播放、同一完整条目重播等情况继续走原播放流程。
- 不涉及响度均衡、采样级无缝、音频文件/曲库格式、来源协议或跨队列事务。

## 本草案提出的设置与反馈

以下为实现方建议，随本设计一并交用户确认：

- 新增 `manualCrossfadeDurationMs`，独立提供 0–12 秒、1 秒步进；默认 0 关闭，旧设置迁移为 0。
- 现有 `crossfadeDurationMs` 继续只控制自动下一首。两项时长以及短淡入淡出开关互相独立，避免必须开启自动渐变才能使用手动渐变。
- 界面明确称为“自动下一首交叉渐变”和“手动切歌交叉渐变”，后者说明仅当前队列适用。
- 等待新曲时保留旧曲标题、实时进度、歌词、媒体会话和播放状态；在已有播放状态区域显示“正在准备切换至…”，反馈属于当前手动请求，取消或迟到结果不能恢复旧提示。不新增页面或复杂布局。
- 准备失败通过现有提示机制说明“未能切换，当前歌曲继续播放”；不能把旧曲设置为播放失败，也不能进入旧曲的媒体重试链。

## 手动请求与双通道生命周期

1. 记录旧曲完整身份和实时状态，建立手动请求代次、目标身份及队列修订；显示准备反馈。
2. 通过既有有界解析、URL 租约和 `prepareTrack()` 准备一个备用通道。旧曲保持原增益，不能先短淡出、停止或重置旧曲。
3. 准备完成后复查代次、队列身份/修订、来源 epoch 和地址租约。只有当前请求仍有效才交接。
4. 手动交接不等待旧曲接近结束；有效时长取请求时设置、旧曲剩余墙钟时间与新曲可播放墙钟时间的最小值。少于 1 秒、时长未知等不具备长重叠条件时，仍保留“准备期间旧曲继续、准备失败留旧”的保护；新曲首次有效播放时做无长重叠的交接，不能先停止旧曲再重复解析。有效准备结果与未过期地址应复用。
5. 新曲首次有效 `playing`、渐变开始时，才提交 `currentIndex`、进度/歌词/媒体控件归属和一次实际播放记录。准备中的目标不进入已播放历史。
6. 完成后释放指定旧通道。完成前新曲失败而旧曲仍可播放时，恢复旧曲实时进度、身份和相关状态；已实际开始的新曲保留播放历史，与自动交接规则一致。

暂停、变速、输出设备、主音量、静音、EQ 等沿用引擎的共享控制和等功率曲线，不增加第三个通道。渐变时长按墙钟时间计算，调快播放速度时不能让曲线超过任一媒体的剩余可播时间。

无长重叠交接也必须先确认新曲有效播放，再释放旧通道。如果通过零时长 `CrossfadeOperation` 实现，`started` 的提交机会必须先于 `completed` 清理，不得因零时长同步完成而丢失当前曲目提交。引擎不具备准备/交接能力或本设置关闭时，才沿用原有单通道路径。

## 连续点击与随机模式

- 准备期间的新点选或导航替代前一请求；立即取消旧解析/预载。当前实际播放曲在新曲发声前保持不变。
- 连续下一首从最近一次请求目标继续导航，而不是每次从尚未交接的旧曲重新选择。需要独立的待切导航游标，不能提前改 `currentIndex` 充当游标。
- 准备期间点上一首按待切游标向后退；退回实际旧曲时取消待切并保留旧曲当前进度。没有待切请求时，采用前述大于 3 秒重播规则。
- 随机模式中，一次导航只抽取一次。尚未发声的目标不得进入实际随机播放历史；连续导航中被替代的抽取先暂存，避免马上返池导致下一次又抽到同一目标。
- 当前导航链提交、失败或取消时，将未实际播放且仍在队列中的保留项按原抽取顺序放回随机池前端一次，排除当前已发声项并去重；已经发声的目标不归还。准备期间的上一首先撤回本链最近的导航，不能提前消耗实际已播放历史。
- 同一目标重复请求不建立重复预载。明确点选当前实际播放条目按现有重播规则处理；导航撤回到旧曲则保留实时进度，二者按入口意图区分。

## 与自动下一首协作

- 手动与自动共用“最多一个备用通道”的约束，必须明确预约来源，不能同时建立两份预载。
- 下一首命中尚未交接的现有自动保留目标时，消费该目标而不重新抽随机；有效的在途解析或已准备 token 可转为手动交接，同时刷新手动意图和旧曲状态快照，避免沿用更早的状态。目标不同则取消旧预约，正确归还未使用的随机保留项。
- 手动准备期间不再启动自动预约。手动失败后恢复从当前实际播放位置/模式选择自动下一首，不得让失败的手动点选劫持后续自动目标。
- 同一请求不得形成自动重试循环。若自动目标正是刚失败的手动目标，本首内不再渐变预载该目标；自然结束时仍可按原有有界加载/错误处理执行。
- 已开始渐变时收到新手动请求，立即调用当前交接的完成语义，保留已提交新曲、收束增益并释放更旧通道；随后从当前已提交曲准备最新目标，不等待原曲线剩余时间，始终最多两个通道。例如 A→B 中请求 C，则立即收束到 B，再准备 B→C；C 准备失败时保留 B，不复活已释放的 A。

## 取消、失败和边界

| 场景 | 行为 |
| --- | --- |
| 准备中暂停 | 取消手动目标和准备反馈，暂停旧曲；恢复时继续旧曲，不迟到播放被取消目标 |
| 准备中 seek | 取消手动目标并定位旧曲 |
| 渐变中暂停/恢复 | 同时冻结/恢复两通道与曲线 |
| 渐变中 seek | 保留已提交新曲、结束旧通道，再定位新曲 |
| 停止、清空、新队列、退出 | 使请求代次失效，清理预约、反馈及两通道；不允许迟到事件改变当前状态 |
| 队列编辑或删除目标 | 按修订及完整身份取消无效预约；删除当前播放项遵循已有规则，不按旧下标播放新位置条目 |
| 旧曲在新曲发声前自然结束 | 如果手动请求仍有效，正常结束路径只推进一次到该手动目标；否则按原有结束路径；不把已结束旧曲恢复为播放中 |
| 新曲在已交接后失败 | 只在旧曲仍可播放且旧身份有效时回滚；不能复活已释放通道，不能同时触发第二条恢复链 |
| 改手动时长为 0 | 已开始的手动渐变立即完成；仍在准备的手动目标转原有切歌流程继续执行，不能吞掉已表达的选歌意图 |
| 改其他时长/开关 | 非零新手动时长影响后续请求；自动时长开关不取消手动交接，手动开关不取消自动交接；短过渡开关仍独立 |

等待及错误反馈必须绑定同一请求代次，过期请求既不能播放，也不能清掉或覆盖较新请求的反馈。

## 实现边界与验收

预计涉及共享设置、主/渲染默认值、设置页与 App 同步、Player Store 和当前队列点选边界，以及已有播放状态文本。复用 `AudioEngine` 的可选准备/交接接口、`CrossfadeController`、租约检查和完整歌曲身份；不另建解析器或随机算法。内部类型、反馈区域具体位置及测试夹具组织交实现方决定，但须满足上述可见行为。

必要自动覆盖：

1. 设置默认/迁移/边界及三个过渡开关独立；关闭时全部既有路径保持。
2. 当前队列下一首、真正上一曲和筛选后点选；跨队列、恢复和重试不误入；当前条目重播与大于 3 秒上一首规则。
3. 长时间解析/缓冲期间旧曲持续播放；失败不污染旧曲错误链；有效发声提交与完成前失败回滚。
4. 连续下一首、上一首撤回、快速点选、同目标去重；随机只抽一次、未发声目标归还且不污染播放历史。
5. 自动预约转手动、不同目标取代、手动失败后的自动行为、来源/队列代次变化。
6. 准备及渐变中的暂停、seek、停止、设为 0、旧曲提前结束、短曲/未知时长的受保护无长重叠交接、零时长开始/完成次序、倍速和迟到事件。
7. 使用 `tools/build-test.mjs` 和项目离线 runner 执行生产 bundle 回归；生成音频的原生 Electron 探针验证两通道时钟、身份交接与旧通道释放。

真实音源与人工听感分别记录，不能用生成音频、零音量媒体时钟或 UI 状态代替听感通过。本批仅在设计批准后创建隔离实施工作区和实施计划；提交、合并与发布按用户后续授权执行。

## Builder Check 处理

- 独立检查及修订复核已完成，原两项规划问题均明确，无关键遗漏。
- 已确认规则的细化：短曲和未知时长的退路继续保护旧曲，准备失败不能提前切断；只省略长渐变，不省略准备与有效播放确认。
- 实现方裁定：渐变中收到新请求立即收束当前交接，沿用 0.6.0 的 `finish()` 即时语义；不延迟用户的新操作。
- 实现方裁定：未播放随机保留项按原抽取先后归还池前端；手动和自动采用独立时长、默认关闭。这些选择随本草案一起交用户确认。
