# OR8：异步写入后的待写入快照保护

日期：2026-10-16。接续[待写入容量保护](OR8-pending-capacity.md)保留的“旧写入清理新选择”边界，对应 OR-10、RR08、RR16。

## 根因与最终行为

原单次 commitAssetWrite 成功后按歌曲和类型 dropFor，批量 assetsWritePending 最后又按相同键 removeEntries。写入旧歌词期间暂存新歌词，或者批次取出旧内容后、该曲实际开始写入前重新选词，这两处清理都会删除新的待写入项。

现在 add 复制记录及嵌套 image，每次暂存生成新的对象版本，包括文本和时间完全相同的重新选择。removeEntries 只消费当前记录仍与传入快照对象相同的条目，供同一个服务实例的 load/list 快照使用；不把来自 renderer 的序列化对象当作清理授权，也没有改变持久化格式。

共享 withPendingAssetWrite 在 IO 前捕获快照。单次手工写入使用这时已有的待写入项；两个批量入口必须传原来选择内容时的快照，未选择待写入内容则明确传空数组，避免写旧内容时重新捕获并清除新选择。成功且非试运行才清理，失败或抛错保留原条目。批次末尾的清理也执行快照比较。

独立复核补出一个关联问题：CAS跳过旧条目后，原丢弃流程仍登记旧文本指纹，会使同内容的新选择被视为已拒绝。现以 discardEntries 在一次串行变更中核对快照、移除并记录实际丢弃项，成功后只为实际移除项清理歌词缓存。过时丢弃既不删除，也不登记拒绝指纹。

## 证据

生产模块通过 tools/build-test.mjs 打包，新增 pending-asset-write.ts 已加入入口。新 pending-asset-snapshot.test.mts 共14项，加既有容量套件9项，受控局部回归23/23通过：

- 迟到清理保留后来歌词、封面及无关条目，重启内容一致；当前快照仍可正常消费。
- 同对象重新add、同文本同时间重选仍是新版本，旧快照不能删除。
- Promise闸门在写入生命周期中暂停，期间重新暂存，完成后保留新选择。
- 批量原快照和显式空快照不获得后来选择的清理权限。
- 成功写入只移除相应歌曲/资源类型；失败、抛错与试运行保留。
- 原子丢弃只消费匹配版本，同文本新选择不被标为已拒绝；原子写盘失败时待写入状态和拒绝指纹均不发布，恢复存储后可以重试。

最初4项在旧生产模块中全部复现误删而失败；修复后通过。原子丢弃接口也先确认缺失回归失败再实现，随后用写盘阻挡验证失败一致性。局部日志：`.cache/pending-asset-snapshot-red.log`、`.cache/pending-asset-snapshot-green-final.log`。

测试全部使用生成临时队列与注入的写入回调，不写日常歌曲、不运行真实源或联网。这里证明的是生产写入生命周期和队列的数据一致性，不是新增真实标签写入或产品UI人工验收；既有asset-export套件继续覆盖原来的落盘行为。

最终 `npm run verify` 退出0：类型检查、生产构建、87/87离线套件、5/5门禁通过，日志为 `.cache/pending-asset-snapshot-verify-final.log`。独立复核指出的丢弃指纹问题修复后再次确认无新增阻断项。`git diff --check` 通过，GraphFlow增量索引已执行。未提交、推送、安装或发布。

## 保留边界

- 快照只能在同一个store实例中使用且不得自行修改。重启后应重新load，不能拿旧实例或跨IPC复制的对象删除当前条目。
- 多个并发任务同时写同一个音频文件的内容先后顺序、任意损坏队列的恢复策略、跨实例同时写目录仍未在本轮解决。
- 本轮没有改变歌词本地优先规则、写标签授权或已有容量数值。听感、日常实际资料交互、真实源更新回退、安装升级仍按OR8原有未验收项保留。
