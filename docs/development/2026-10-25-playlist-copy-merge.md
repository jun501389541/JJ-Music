# 普通歌单复制与合并实施记录

2026-10-25。用户先选择“复制、合并均新建歌单，保留原列表”，独立Builder Check无重要缺口后，再明确批准[具体设计](../superpowers/specs/2026-10-25-playlist-copy-merge-design.md)。按[实施计划](../superpowers/plans/2026-10-25-playlist-copy-merge.md)实施，保留原有QQ歌单搜索及三平台刷新回归等未提交改动。

## 使用与资料规则

歌单管理 → 批量管理 → 勾选普通歌单 → 复制或合并 → 核对预览 → 明确确认。默认列表/收藏继续禁选；复制至少1个、合并至少2个，最多1000个不同普通歌单。筛选和选择变化会失效旧预览。

复制按当前歌单显示顺序创建独立新ID，名称加“（副本）”，最长4096字符；保留每首资料、顺序、远程来源关联和既有封面引用，不复制文件。合并可填写trim后1–128字符名称，按显示顺序再按各歌单内部顺序，以playlistEntryKey去重保留第一份资料；本地/在线/跨平台独立。合并新歌单source=local，没有远程歌单关联和继承封面。

上限为去重前50000首，输入和输出资料各20MiB。输入先计数、逐条累计大小并预留快照封装开销，再克隆；超限整批拒绝，不截断。来源快照在Store队列中一致读取；主进程保存候选，渲染层只能提交操作、ID顺序、名称和token，不能注入曲目或路径。

单候选租约10分钟，支持时钟倒退拒绝、精确token丢弃、代次/取消与离页清理。确认同步消费token，Store在实际排队保存点检查维护状态及所有来源revision；源变化则整批拒绝，不因无关歌单变化丢失其修改。一次mutation、一次原子写入生成整批，不循环create/addTracks。

资料迁移开始时清理候选、阻止新的派生操作，并等待在途歌单写入再复制；保存点再次检查退出、迁移和重新定位维护锁。正常退出清候选并沿用Store.flush等待在途保存。只新增派生功能所需互斥，不修改系统功能或日常资料。

保存成功但列表刷新失败会明确提示已创建、无需重复操作。来源列表、收藏、默认列表、侧栏自定义顺序、当前队列和音乐原件不改变。修改合并名称需要重新生成预览。
